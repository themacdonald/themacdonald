## My evaluation philosophy (how I work)

**Reliable systems come from measurable quality.** My approach:

1) Define quality as a rubric (what “good” means)  
2) Measure consistency (agreement, drift, error types)  
3) Build a feedback loop (sampling, adjudication, retraining, monitoring)  
4) Ship the system as repeatable tooling (CLI, reports, dashboards)

**Quality signals I track**
- Inter-annotator agreement (Krippendorff’s alpha / Cohen’s kappa)
- Error taxonomy rates (hallucination, omission, wrong tool use, policy errors)
- Reviewer drift and calibration (before vs after)
- Slice performance (language, domain, sensitive attributes where applicable)
- Regression testing for prompts and model versions

## Repo standards (what you can expect in my work)

Every serious repo follows the same structure:

- `README.md` with problem, approach, and reproducible demo  
- `data/` with sample dataset or generator  
- `src/` with modular Python code  
- `cli/` with commands like `evaluate`, `report`, `audit`  
- `reports/` with HTML + JSON outputs  
- `tests/` minimal regression coverage  
- `Makefile` or `taskfile` to run everything in one command

If a repo is missing this, it is still in active build.
